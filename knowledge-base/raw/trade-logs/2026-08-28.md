### Code-level verification (per `feedback_label_empirical_audit` — not deduced from aggregates)
The 08-27 pre-Tokyo briefing raised "OANDA Open Trades = 0 yet `hedge_block` fires 233×" and the same day's strategy report hypothesised an **OANDA/ledger desync bug** as top priority. **Read against the code, that hypothesis is wrong.**

`modules/demo_trader.py:4915-4928`:
```python
_hedge_opposing = None
for _ot in _mode_inst_live + _mode_inst_shadow:     # ← live AND shadow
    if _ot.get("direction") and _ot["direction"] != signal:
        _hedge_opposing = _ot.get("direction")
        break
if _hedge_opposing is not None:
    ...
    _block(f"hedge_block({_base_mode}/{instrument}:{signal})")
```

`_mode_inst_shadow` (L4877) selects open trades with `is_shadow == True`. The gate iterates the union and blocks regardless of layer. The in-line comment states this is deliberate:

> `# 2026-04-30 (rule:R2 / H2): shadow バイパスを撤廃。… ヘッジは Live/Shadow 問わず常に block する。`

**And the live state matches exactly.** `/api/demo/status` shows `open_trades` = **6 rows, every one `is_shadow: 1`** (4× `sr_anti_hunt_bounce` EUR_JPY, 1× `dt_sr_channel_reversal` GBP_USD, 1× `doji_breakout` EUR_USD), while the OANDA heartbeat reports `open_trade_count: 0` and `margin_used: 0.0000`. There is **no desync**: the broker count counts broker positions, the internal book holds shadow positions, and `hedge_block` is designed to see both.

**Not a bug — but a decision worth taking.** The documented rationale (R2/H2) is about protecting shadow-sample quality: recording opposite-direction samples at the same instant lets score-max selection admit the losing strategy too, corrupting inter-strategy ranking. That is a real concern. The side effect is that **a shadow position can suppress a live candidate**, which under shadow-first is backwards — and at 35.4% of all blocks it is now the single largest source of suppression in the system. Filed for user decision, no code touched.
