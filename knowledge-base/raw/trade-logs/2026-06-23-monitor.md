## Alert: 09:38 UTC

### 検出された問題
- 🚨 STATUS API取得失敗: HTTP Error 502: Bad Gateway
- ⚠️ **直近4時間トレード0件** かつ全モードWAIT — 発火条件を満たしていないか、フィルターで全遮断の可能性

### 診断
## 原因分析

### 推測（確認前）

**502 Bad Gatewayについて**
- リバースプロキシ（Nginx/HAProxy等）がバックエンドのAPIサーバーへ到達できていない
- APIサーバープロセス（uvicorn/gunicorn等）がクラッシュまたは停止している
- メモリ/CPU枯渇によりワーカープロセスが強制終了された可能性
- デプロイ・再起動中のタイミング問題

**トレード0件・全モードWAITについて**
- APIが死んでいるため正確なステータス取得自体が不能であり、**この症状はAPI障害の副次的結果**である可能性が高い
- ただし独立した問題（フィルター過剰・発火条件未達）が並存している可能性も否定できない

---

### 確認事項（優先順）

**【最優先】インフラ層**
- [ ] APIサーバープロセスの死活確認（`ps`, `systemctl status`, `docker ps`等）
- [ ] プロキシ（Nginx等）のエラーログ確認
- [ ] サーバーリソース確認（メモリ・ディスク・CPU）
- [ ] 直近のデプロイ・再起動履歴の有無

**【次点】アプリ層**
- [ ] アプリ側のエラーログ・クラッシュログ確認
- [ ] DB/外部依存サービス（ブローカーAPI等）の接続状態確認

**【トレード停止の独立確認】**
- [ ] API復旧後にステータスを再取得し、WAITの原因（フィルター設定・発火条件・時間帯制限等）を改めて精査

---

### 対処方針

1. **まずAPIサーバープロセスを再起動**し、502が解消するか確認
2. 再起動で解消しない場合はプロキシ設定・ポートバインドを確認
3. 解消した場合でも**根本原因（なぜ落ちたか）をログで必ず特定**し、再発防止策を打つ
4. API復旧後にトレード停止が継続している場合は、フィルター・発火条件の問題として**切り離して調査**
5. 監視アラートにAPIヘルスチェック（プロセス監視）を追加し、次回は早期検知できる体制を整備
