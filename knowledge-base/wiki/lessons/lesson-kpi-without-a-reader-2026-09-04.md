# lesson: KPI を定義しても読み手を作らなければ、符号が反転しても誰も気づかない (2026-09-04)

**発見日**: 2026-09-04 | **rule**: R3
**関連**: [[m1-kpi-readout-and-mechanical-flip-2026-09-04]] / [[lesson-live-fill-estimand-shadow-conflation-2026-09-03]] / [[roadmap-v2.3-payoff-friction-repair]]

## 問題

roadmap v2.3 の最重要 KPI **M1 (clean live 30d rolling PnL > 0)** を
再計算する主体がプロジェクトに存在しなかった。M1 は 2026-07-06 に手動で一度測られ
(N=92 / −242.6p)、その値が roadmap の表に書かれたまま **60 日間凍結**した。

## 症状

- roadmap の M1 行は「**−242.6p (未達)**」と表示され続けた
- 実際には **2026-08-31 前後に符号がプラスへ反転していた** (09-04 実測 N=15 / +19.8p)
- 反転を誰も観測しなかった。日次レポートも監視スタックも M1 を見ていない

既存主体は全て**別の量**を測っていた:

| 主体 | 測っているもの |
|---|---|
| `clean_n_tracker` | セル別 clean **N (件数)** |
| `daily_live_monitor` | ELITE_LIVE 追跡 / **cutoff 以降の累計** |
| Tier B daily report | **前日** PnL |
| `anomaly_watcher` | **鮮度・停止・生存** |
| `prereg_trigger_watch` | **registry トリガ** (M1 は registry に無い) |

## 原因

MEMORY に既に 3 領域ぶんの「収集したのに読み手がいない」教訓がある
(MoF URL/write-only、engine tick 検知器の配線欠落、freshness UI)。
しかし今回はその**一段手前**だった:

> **収集経路の write-only** ではなく、**指標そのものに読み手が無い**。
> 「roadmap の表に数字を書く」ことは計測ではなく、**一度だけのスナップショット**である。

## もう 1 つの発見 — rolling 窓の符号は成果ゼロでも反転する

読み手を作って初めて分かったこと。08-30 → 09-01 の符号反転を差分分解すると:

| | N | 寄与 |
|---|---:|---:|
| 新規に窓へ入った約定 | **0** | **0.0p** |
| 窓から抜けた約定 | 1 | **−123.2p** |

**新規約定ゼロのまま、2026-07-31 の −123.2p が 30 日窓の外へ落ちただけ**で
KPI の符号が反転していた。符号だけ見れば「黒字転換」に見える。

さらに符号自体が測れていない: bootstrap P(sum≤0)=0.426、
**15 件中 4 件は、その 1 件を抜くだけで符号が消える**。

## 修正

- `tools/m1_clean_live_monitor.py` — M1 の唯一の SSOT 計算主体。
  verdict を 3 状態 (`MET` / `MET_UNDERPOWERED` / `NOT_MET`) にし、
  **符号反転の帰属** (新規 vs 窓外脱落) と **1 件脆弱性** を毎回併記する
- `tools/quant_gate_status.py` (日次 Tier A cron) へ配線。
  Discord は 1900 字で切るので **M1 セクションは先頭固定**、順序をテストで pin
- estimand 4 条件・配線・順序・帰属・seed の counterfactual **10/10 が落ちる**ことを確認
- M1 の**定義は変えない** (定義変更は user 決裁)。生の符号に解像度を併記するのみ

## 教訓

1. **KPI を定義したら、同じコミットで「毎日それを再計算する主体」を定義せよ。**
   ドキュメントの表に書かれた数字は計測ではなくスナップショットであり、
   **書いた瞬間から stale になる**。「収集済み ≠ 監視済み」の一段手前に
   「**定義済み ≠ 計測済み**」がある。
2. **rolling 窓の指標は、必ず符号変化を「新規流入」と「窓外脱落」へ分解して報告せよ。**
   分解しないと「古い負けが抜けただけ」を「改善した」と読む。
3. **閾値のみの KPI は分母が縮むと縮退する。** M1 は「合計 > 0」しか要求しないので、
   負けセルを止めて分母を縮めるほど達成しやすくなる — 意図と逆向きのインセンティブ。
   閾値 KPI には必ず N か検出力の資格条件を併記して読む。
4. **読み手を足すときは「出力が実際に読み手まで届くか」まで見よ。**
   Discord の 1900 字切り詰めのような下流の制約を無視すると、
   読み手を作っても write-only と実質同じになる。
