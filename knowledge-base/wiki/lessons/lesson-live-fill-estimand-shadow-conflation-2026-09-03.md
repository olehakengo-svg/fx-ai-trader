# 教訓: 「約定」を名乗る検知器が shadow を数えていた (2026-09-03)

**rule:R3** / 発見: autopilot セッション 2026-09-03 / 関連 PR: 本セッション

## 一行

**``live_n_stagnation`` は名前も estimand 表も「約定が出たか」と言っていたが、
実装が読んでいた行の 99.8% は shadow だった** — LIVE 約定が 7.5 日ゼロでも
永久に沈黙する構造で、実際に沈黙した。

## 何が起きたか

セッション開始プロトコルの「直近 12h トレード活動」確認で、**LIVE 約定
(``oanda_trade_id != ''``) が 2026-08-26 14:59 UTC を最後に 133 市場オープン
時間 = 実時間 7.5 日ゼロ**であることが判明した。この間:

| 検知器 | 出力 |
|---|---|
| `live_n_stagnation` | `[]` (無音) |
| `candidate_stagnation` | `[]` (無音) |
| `engine_tick_stall` | `[]` (無音) |
| 画面 `trade_row` (「約定行」) | **ok / 15 分** |

9 個の検知器のいずれも鳴らず、画面は緑だった。

## 原因: estimand の取り違え (実装ではなく**記述**が偽だった)

``demo_trades`` は shadow 行と LIVE 行を同居させている。本番実測で
**501 行中 LIVE は 1 行 = 99.8% が shadow**。shadow は毎日 80-111 行流れる。

``check_live_n_stagnation`` は ``/api/demo/trades?limit=500`` の**全行**から
最新時刻を取る。したがってこの検知器の「最終行」は LIVE が完全に止まっても
常に数分以内であり、**約定の停止を原理的に検知できない**。

にもかかわらず、``check_engine_tick_stall`` の docstring にある
**estimand 一覧表** (この系列の canonical な参照点) はこう書いていた:

```
``live_n_stagnation``       約定が出たか (ゲート通過後)              24h
```

実装は一度もそれを測っていない。**表が実装について偽を述べていた。**

同じ畳み込みが画面側にもあった: ``modules/freshness_policy.py`` の
``trade_row`` 系列はラベルが「約定行」で、SQL は
``SELECT MAX(created_at) FROM demo_trades`` — フィルタ無し。

## なぜ 2026-08-26 の「修復」で直らなかったか

``live_n_stagnation`` は **2026-04-22 から 126 日間 no-op** だった
(存在しない ``status["last_trade_time"]`` を読んでいた)。2026-08-26 に
実データ経路へ書き換えて「修復」した。

しかしその修復は **field 契約のバグを直しただけで、母集団を間違えた**。
結果、検知器は「一度も鳴らない」から「**名乗っている理由では一度も
鳴らない**」に変わっただけだった。

> **修復の検証は「動くか」ではなく「名乗っている estimand を測っているか」で行う。**
> 前者は 2026-08-26 に確認され、後者は確認されなかった。

これは KB の既存教訓 (2026-09-02) 「**妥当性チェックは性質を pin せよ、
時変の代理を pin するな**」の同系列 — 今回は *代理を estimand と取り違えた*
形で、通算 3 領域目。

## 対処 (本 PR)

1. **新検知器 ``live_fill_stagnation``** — ``oanda_trade_id`` を持つ行だけを見る
2. **サーバ側集計** (`get_row_freshness` に第3系列 `live_fill` を追加) —
   watcher の 500 行窓は shadow に埋め尽くされ**実測 7.67 日しか遡れない**。
   ドリフトがそれを超えると最後の LIVE 行が窓から落ちて計算不能になる
   (2026-09-03 時点で窓の先頭は最終約定の 3.5 時間前 = 崖っぷちだった)。
   **読み手はあるが窓が狭すぎる**型 = PR #213/#214 と同型
3. **estimand 表の訂正** — 1 行目を実装に合わせ、約定の行を新設
4. **画面ラベルの訂正** — 「約定行」→「トレード行 (shadow込)」+「LIVE 約定」を新設

## 閾値較正 120 市場オープン時間

本番 6,000 行 (2026-06-24〜09-03) から LIVE 約定 63 件 / 到着間隔 62 本を実測:

| 母集団 | n | median | p90 | max |
|---|---|---|---|---|
| 全期間 | 62 | 5.0h | 43.2h | **224.7h** |
| carve-out 後 (2026-07-29〜) | 15 | 30.0h | 65.8h | **75.3h** |

**全期間 max 224.7h は較正から除外した** — これは 2026-07-15→07-29 のギャップで、
``_is_xau_inst`` バグが preserve 型 LIVE 送信を 3.5 ヶ月殺していた時期の末端
(PR #119→#124 で修復、直後の 07-29 04:44 が次の約定)。**現行構成に存在しない
母集団**である。

> ⚠️ **消滅した構成のギャップを較正に混ぜると、閾値が過去のバグの尾で膨らみ
> 本物のドリフトを見逃す。** 2026-09-01 の候補行較正で踏んだ「max の 3 倍」
> (週次 金→月 再開ギャップを見落として過大に見積もった) の**鏡像**。
> 同じ「母集団の取り違え」が、あちらでは閾値を緩め、こちらでは緩めかけた。

replay 結果:

| 閾値 | carve-out 後の誤発火 | 全期間の発火 | 09-03 の実ドリフト (133.3h) |
|---|---|---|---|
| 72h | **1 回** | 2 | 捕捉 |
| 96h | 0 | 1 | 捕捉 |
| **120h** | **0** | **1 = preserve バグの尾 (真陽性)** | **捕捉** |
| 144h | 0 | 1 | **見逃す** |

120h = carve-out 後 max の **1.59 倍**。全期間で唯一の発火が既知バグの尾＝
**この検知器が当時あればあのバグを捕捉できた**ことの retrospective な検証。

⚠️ n=15 は薄い。**誤発火が出たら上げる** (下げるのは実測を取り直してから)。

## counterfactual (7/7 が所望どおり失敗)

| # | 変異 | 落ちるべきテスト | 結果 |
|---|---|---|---|
| 1 | `main()` の配線削除 | 配線 pin 2 本 | ✅ |
| 2 | SQL の `oanda_trade_id` フィルタ削除 | DB 行動 pin 2 本 | ✅ |
| 3 | 閾値 72h (実測 max 割れ) | 較正 pin | ✅ |
| 4 | 閾値 200h (見逃し) | 発火 pin + 較正上限 pin | ✅ |
| 5 | 週末除外を実時間に | 週末 pin | ✅ |
| 6 | `unparseable` を総括 return に畳む | 沈黙禁止 pin | ✅ (下記) |
| 7 | 閾値を watcher にベタ書き | SSOT pin | ✅ (下記) |

### ⚠️ counterfactual 6 と 7 は**初回に素通りした** — 両方とも本物の穴だった

- **6**: `no_rows` の早期 return を消しても全テスト green。理由は下の
  `if st != "ok": return events` が全部飲み込んでいたから。つまり
  `no_rows` 分岐は死にコードで、**同時に ``unparseable`` (= 行はあるが時刻が
  壊れている = 本物の異常) まで黙って捨てていた**。本 PR が直している
  「静かに skip」型の穴を、新しい検知器に作り直すところだった → 明示分岐 + テスト追加
- **7**: `aw.X is fp.X` だけを見ていたが、watcher に `= 120` とベタ書きしても
  **120 は CPython の小整数キャッシュ域なので `is` が True** になり green のまま。
  値の一致では「書き写し」を検出できない → **束縛が `_fp` 由来という構造**を pin

> **counterfactual が初回に通ったら「安全」ではなく「pin が無い」の証拠** —
> MEMORY に 2 例記録済みだったところへ **3 例目・4 例目**。しかも今回は
> 2 件とも**実装側の実欠陥**を伴っていた (死にコード + 沈黙経路 / 無効な pin)。

## 発火時の読み方 (重要)

**``live_fill_stagnation`` の発火 = バグとは限らない。** 「LIVE 資格セルが
1 つも条件を満たさなかった」も同じ見え方をする (``candidate_stagnation`` と
同じ注意)。

実際、今回の 133h ドリフトの実体は**シグナル枯渇**であって転送障害ではない。
直近 8 日の LIVE 資格ファミリの発生数:

| entry_type | shadow | live |
|---|---|---|
| `price_shock_rev_aud_jpy_h1_long` | 1 | **1** (08-26 の約定) |
| `usdjpy_carry_dip_accumulator` | 1 | 0 |
| `price_shock_rev_eur_gbp_h1_long` | 0 | 0 |
| `weekend_gap_fade` | 0 | 0 |
| `kalman_d7` | 0 | 0 |

同期間の shadow 総数は 536 行 — つまり**エンジンは動いており、LIVE 資格の
無いセルばかりが鳴っている**。08-26 の約定が転送経路の健全性を実証している。

→ 発火時の切り分けは ``block_counts`` と LIVE 資格セルの現況で行う。
**発火そのものを engine 異常と読んではならない。**

## M1 への含意

これは監視の話にとどまらない。**LIVE 資格セル群の発生率が ~1 件/週まで
落ちている**ことは、roadmap v2.3 の M3 (「clean live N≥30 セルを 3 個」= 現在 0 個)
がスループット側から見えている姿である。月次符号転換 (M1) は、
**符号以前に母数が足りない**。
