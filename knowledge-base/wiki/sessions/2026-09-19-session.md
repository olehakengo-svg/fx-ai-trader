## 3. 同 PR 第 2 コミット — GDELT の soft 分類 + 撤回済み主張の残存 (指摘 6 件の消化)

### GDELT (#261) — 指摘が名指ししていない第 3 の失敗形が本体だった

指摘「全例外が soft に落ちるので恒久障害も alert に乗らない」は ✅ 確定。
soft 判定を「ソース名」から「**ソース名 ∧ 例外形状**」へ変え、
`unexpected GDELT response` (上流恒久変更の署名) と `OSError` は hard に。
**列挙に無い形状は hard = fail-closed** (文字列判定である以上、
過剰 alert 側に倒れる方が黙って stale で残るより安全)。

🔵 さらに実測で**例外軸からは永久に見えない形**を見つけた:
GDELT は **HTTP 200 + 正当な CSV ヘッダのまま系列が進まない**。
committed CSV の末尾は **2026-09-13** / 3,518 行で、**09-18 の run は "success" で
同一の 3,518 行を書き diff ゼロ** ⇒ 本日時点で **6 日 stale なのに監視は無言**。
soft 分類の前提「全範囲を毎回再取得するので自己修復する」は上流が止まると成立しない。

⚠️ **自己訂正**: 当初「GDELT は 5-6 日ラグがあるはず」と推測した。
`commit 日 − 系列末尾日` を git 履歴 **16 commit** で測ると **median 0 / max 1 日**で、
推測は誤りだった。stale は内在ラグではなく**実際の異常**。
**閾値を置く前にラグ分布を測った**ことで、誤った threshold と誤った安心の両方を回避した。
`GDELT_STALE_DAYS_MAX = 3` は観測 max の 3 倍。誤発火が出たら閾値は**上げる**。

pin は**実観測の curl メッセージ**で固定した — 既存 pin は `"http 429"` という
作り物の文字列を使っており、「429 は soft」という**覆域の錯覚**だけを残していた。
