## Phase 2 — 未解決事項の最上位を実装 (rule:R3)

**`last_trade_row_age` / `last_candidate_row_age` を `/api/demo/status` に出す** を実装。
設計判断と実測根拠は [[changelog]] 2026-08-27 の項に集約。要点のみ:

- 判定列は `created_at` (DB DEFAULT で必ず埋まる)。`bar_time` は PR #204 の全 NULL 前例により不採用。
- status を **5 値** (`ok`/`no_rows`/`no_table`/`unparseable`/`error`) に分離 — 「行が無い」と
  「クエリが落ちた」の混同を構造的に禁止。
- `error`/`now` は `row_freshness_*` へ名前空間化 — 汎用 `error` キーとの衝突で
  「鮮度クエリ失敗」が「status 全体の失敗」に化けるのを防ぐ。
- **field を足すだけで終えない**: 読み手として `candidate_stagnation` 検知器を同一コミットで併設。
  C1 テーブルが 4 ヶ月 write-only だった同型を繰り返さないため。
- 検知器の閾値 6h は**バースト間ギャップ**の実測 max 120.3 分 (水 22-00 UTC の薄商い) の 3 倍。
  ⚠️ **初稿の統計を自己訂正**: 素の行間隔 (median 0.10 分) は*バースト内*密度であって停止判定の
  ケイデンスではない。候補行は 1 バーで複数戦略ぶんが一斉に書かれる (2,000 行 = 16 バースト)。
  正しい指標は**バースト間** median 3.2 分 / p90 59.7 分 / max 120.3 分。閾値の値 6h は不変だが
  **実効 N=16** の粗い推定 = 暫定。1〜2 週後に取り直す。誤発火時は**上げる**方向のみ。
- **自己検証の経緯**: デプロイ後に候補行が 31 分増えないのを見て「定数固着はコードを疑え」を
  自分の計測に適用 → バースト構造に気付いた。当時の 70 分ギャップは p90 と max の間 =
  **異常ではなかった**。初稿の median 0.10 分を信じていれば異常と誤断していた。

**counterfactual 4 本**で全テストが実際に落ちることを実行確認 (green のまま無力化していない証拠)。

## Phase 2.5 — 新検知器の estimand を本番で検証し、主張を弱めた

デプロイ後に `evaluated_candidates` が **73 分ゼロ行**なのを発見 → 事故を疑って追跡した結果、
**benign と確定**:

| 観測 | 値 |
|---|---|
| `tick_counts` | daytrade 40→43 / scalp 105→112 (90 秒で前進) = **エンジン生存** |
| `block_counts` | 03:02 の再起動以降 **154 件** = 候補は entry 段階まで流れている |
| Render ログ | `[DTE] HTF_HARD_BLOCK EURGBP=X htf=bull: 1 blocked -> eurgbp_daily_mr` が連続 |
| `write_probe` | ok (書込み経路は生存) |

→ **DTE 候補が `eurgbp_daily_mr` のみで、その全件が HTF Hard Block に除去されていた**。
候補行は **HTF Hard Block の後**に書かれる (endpoint docstring の estimand 警告どおり)。

**この検知器が測るのは「エンジンが評価しているか」ではなく「候補が select_best に到達したか」。**
通知文言を「engine 停止の疑い」から「benign 要因 (HTF block / 薄商い) を先に潰せ」へ改め、
docstring に確認手順 (Render ログ / tick_counts / 薄商い帯) を明記した。
真の engine 停止判定には `tick_counts` の差分監視が要るが、cron は状態を持てないため**未実装**。
