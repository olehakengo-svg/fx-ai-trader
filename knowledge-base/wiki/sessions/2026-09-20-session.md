## 教訓
- **除外率は分母の選択で意味が変わる**。「raw の何%が捨てられたか」(効率) と
  「独立観測が何本貯まるか」(蓄積) は別 estimand。捨てられた行が独立イベントかを
  機構から確認するまで、除外率を枯渇の原因に使ってはならない
- **レポートが自分で「構造的に衝突している」と書いているのに数値を出し続けるなら、
  それは検知ではなく作文。** 衝突を認識した回で構造を止めること
- **repo に無いツールはテストされない。** 10 週打ち直され続けた ad-hoc スクリプトは
  「毎週動いている」ように見えて品質ゲートの外側にあった
- **「出力で隠す」は「計算しない」ではない。** 禁止の対象が計算なら、ガードは計算の
  **手前**に置く。レビューの P1 はこの一点で、指摘どおり直したら**自分では見つけて
  いなかった leak (戦略集計) が pin に落ちた** — 正しい位置にガードを置くと、
  同じ規約に違反する別経路が自動的に露出する
- **免除条件が「データ次第で成り立つ」なら、それは免除ではなく潜伏バグ。**
  「strict super-set は別 estimand」は他ペアに行がある間だけ真だった
- **閾値の隣に数を置くなら、その数は閾値と同じ母集団で数えたものでなければならない。**
  `n=74` を `N=40` の隣に出せば、読み手は gate 通過と読む。
  **本 PR だけで同型が 3 例出た — estimand の不一致は「他人の欠陥」ではなく常在菌**
- **fail-closed は「入力が壊れる全ての形」を列挙してから書く。** 「読めない」を塞いで
  「読めるが壊れている」を残すのは、対称な反対側の未処理
  ([[feedback_check_the_symmetric_side_2026_09_19]] 3 度目)
- **同じ設定ファイルを読む 2 つ目の実装を書くときは、フィールド一覧ではなく
  「正本の読み取りコード」を仕様として読む。** 本 PR の指摘 7 件中 5 件が
  `prereg_trigger_watch` との契約ズレ (`match` / `reasons_marker` / `count_basis` /
  `active` 既定 / live の暗黙 dedup) で、いずれも正本を読めば事前に防げた
- **over-exclusion は leak の鏡像。** 片側 (漏れ) だけを見ていると、もう片側
  (実在する観測を黙って消す) を見落とす
- **「検査不能を『異常なし』に畳まない」は 1 つの不変条件であって、入力形状ごとに
  個別対応する類のものではない。** 本 PR は fail-open を 3 回 (読めない → 構造不正 →
  キー欠落/空) に分けて塞いでおり、正本は同じことを 1 箇所で表明していた
- 🔑 **指摘は仮説として受け取り、実データで数える。** 「flag-drift 行が混ざりうる」は
