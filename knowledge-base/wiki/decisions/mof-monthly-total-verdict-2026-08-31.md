## 2. user の「7月の負けは介入をくらった」説 — **未決着に戻る**

08-28 時点では直前窓 = 0円 で **07-01〜07-29 は反証済**だった。
しかし user 外部口座のワースト 2 日 **07-30 (−69,628円) / 07-31 (−21,370円)** は
**本窓 (07-30〜08-26) に入る**。本窓の総額は 0 ではない。

したがって:
- 反証されたのは 07-29 まで（変更なし）
- **07-30 / 07-31 は「窓内に介入があった」以上のことが言えず、未決着のまま**
- 総額 >0 の情報量は 0 より弱い（[[mof-monthly-total-check-2026-08-28]] §2 の非対称性）。
  「窓内のどこかに介入あり」までで、当該 2 日への帰属は主張できない

⚠️ **禁止事項**: 価格シグネチャ（レンジ 579p 等）から介入日を推定して帰属を埋めることは、
`mof-next-episode-reverdict` (MoF family #4) の 2026 窓 OOS を burn するため**禁止**
(MEMORY `project_t5_restore_mof_crosslock_2026_08_10`)。決着は四半期開示を待つ。

## 3. 検知の失敗 — 同時に露見した 2 つの欠陥 (本セッションの主成果)

本開示は **08-28 に公表され、08-29 にはリポジトリ内に取り込まれていた**。
にもかかわらず 08-31 の期日到来まで誰も気付かなかった。原因は独立した 2 つ:

### (a) 人手経路: 公表 URL を「推測」していた
08-28 のチェックは、過去 12 窓のページ名がたまたま全て月末営業日だったことから
**命名規則を「月末営業日」と推定**し、`20260831.html` を直接叩いて 404 を得て
「未公表」と結論した。実際の公表は **`20260828.html`**。

正しい命名規則は **`window_end + 2〜4 日`** であって月末営業日ではない
(20260828←08-26 / 20260731←07-29 / 20260630←06-26 / 20260529←05-27 = +2, +2, +4, +2)。
月末営業日との一致は偶然の副産物だった。

> **`index.html` を列挙していれば当日中に見えていた。**
> 構築した URL の 404 は「未公表」の証拠ではない — 「自分が予測した名前では無い」しか意味しない。
> 既存の `tools/mof_interventions_fetch.py` は**正しく index を列挙している**。
> 人手チェックがそのツールを迂回したことが欠陥だった。

### (b) 機械経路: 書き手はいたが読み手がいなかった (write-only 6 例目)
日次 cron (`.github/workflows/mof-statements-daily.yml` → `tools/mof_statements_daily.py`)
は index を列挙して **08-29 のコミット `b27277d1` で
`data/external/mof_statements/interventions_monthly_pending.csv` に
15,399.3 を書き込んでいた**。しかしこの CSV を読む検知器は存在しなかった。

registry 側のエントリは `deadline_info` 型 = **期日まで何も評価しない**。
宣言されていた到達経路も「Claude が公表ページを確認」という人手経路 (= (a)) だった。
結果、**値は 2 日間リポジトリに座ったまま**だった。

これは MEMORY が繰り返し記録している型の再発:
- 「field を足すだけで終えると write-only → 読み手を同一コミットで併設せよ」(PR #207)
- 「検知器を書いても呼ばれなければ全テスト green のまま無音」(PR #208)
- 「静かだった」と「見えていなかった」を区別せよ (PR #210)

### 修復 (同一コミット)
1. **新型 `csv_row_match`** を `tools/prereg_trigger_watch.py` に追加。
   収集済み CSV に述語一致行が現れたら TRIGGERED。
   設計上、**「取得不能」と「一致ゼロ」を折り畳まない** — ファイル欠落 /
   パース失敗 / **列欠落 (schema 変化)** / 述語不正はすべて `DATA_UNAVAILABLE`。
   折り畳むと schema が壊れた瞬間から永久に「健全に監視中」を表示し続ける。
2. **後継エントリ `mof-monthly-disclosure-new-window`** を登録
   (window_end > 2026-08-26 ∧ amount > 0)。日次 cron が書く CSV を Tier-A cron が毎日読む。
3. **回帰テスト**: 実ファイルに対し「08-29 時点の正しい閾値 (window_end > 2026-07-29)」なら
   TRIGGERED になることを固定 = **この検知器があれば当日に捕まえていた**ことの証明。
4. **反実仮想テスト**: `evaluate_trigger()` 経由で評価し、dispatch から分岐を外すと
   `unknown type` で落ちることを確認済 (検知器が実際に呼ばれているかまで pin)。

旧 pin (`type == "deadline_info"` かつ `deadline == "2026-08-31"`) は
**誤った設計そのものを固定していた**ため、「後継が機械評価可能である」という
**性質**の pin に置換した (PR #209 教訓: 構文でなく性質を pin せよ / 緩めるのでなく絞って強くする)。

## 4. T5 復帰第2要件への含意 — 材料は肯定側に転じたが**認定は保留** (R1 = user 決裁)

`t5-jpy-cap-restore-price` の復帰は AND 条件:

| 要件 | 状態 |
|---|---|
| 第1要件: USD_JPY D1 close < 159.50 | 🔴 **成立** (2026-08-03 以降 常時点灯) |
| 第2要件: 介入観測 or 当局の 160 防衛言及 (**外部一次情報のみ**) | 🟡 **肯定側材料を初取得、ただし未認定** |

- 08-28 時点の材料は**否定側** (直前窓 0円) だった。本開示で**初めて肯定側に転じた**。
- 本開示は MoF 公式の外部一次情報であり、**価格推定ではない**ため cross-LOCK に抵触しない。
- **しかし認定には足りない**:
  - (a) 月次開示は**方向を開示しない** — 「円買い介入」と断定できない
  - (b) **介入日が特定できない**ため、「160 防衛」の文脈適合を一次情報で確認できない
- → **lot 0.5x 維持。変更なし。**

**user 決裁事項 (R1)**: lot 1.0x 復帰は Rule 1 (lot↑) であり autopilot は執行しない。
決裁に必要な材料が揃うのは **Q3 四半期日次開示 (~2026-11-06)** で、そこで
介入日と方向が判明する。**それまで待つことを推奨** — 現時点の認定は (a)(b) の
2 つの推定を含み、そのうち日次帰属の推定は OOS burn の禁止事項に接する。
