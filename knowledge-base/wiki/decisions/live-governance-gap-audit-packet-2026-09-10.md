# 実弾ガバナンス監査パケット — 自走マージ → auto-deploy → 実弾 の経路

## 1. 問題設定 (なぜこの監査が必要か)

本プロジェクトの執行経路は **Claude 自走マージ (`gh pr merge --admin`) → main
auto-deploy (Render) → 本番実弾 (OANDA 本番口座)** であり、人間のリリースゲートが
構造上存在しない (自走原則 2026-07-06 user 承認)。この設計自体は user 決裁済みだが、
[[process-meta-audit-2026-09-07]] は主にプロセス効率 (base rate / 欠陥税 / enforcement
不在) を監査しており、**「実弾に到達するコードのガバナンス」そのものは監査次元に
含まれていなかった** (= 監査盲点 2)。

盲点の実在を示す直近の実例:
- **keeper × emergency_kill ギャップ (本起票の契機)**: 実弾を撃つコンポーネント
  (status_volume_keeper、2026-09-01 arm) が最終防衛 (emergency_kill) の管轄外で
  9 日間本番稼働していた。検知は QA/監視ではなく反証レビューの人手
  ([[status-volume-keeper-2026-09-01]] 追記 2026-09-11)
- **同型の既知クラス**: 549250 事故 (運用凍結が実は存在しなかった)、watchdog 再武装、
  LIVE 約定検知の shadow 混同 (PR #221) — いずれも「防御が名乗る範囲を実際には
  カバーしない」= 実弾ガバナンスの検証が名乗りベースで行われてきた証拠
- メタ監査の defect-tax finding: 主要インシデント発見の QA 起点は 0/8 (全て事故・
  手動監査起点) — 実弾経路の欠陥が**構造的に事故でしか見つからない**

## 2. 監査範囲 (scope freeze)

実弾 (OANDA 本番口座への発注/決済) に到達しうる全経路と、その各段のゲート:

| # | 経路/段 | 監査質問 |
|---|---|---|
| G1 | PR → main (自走マージ) | live 経路 PR の識別は機械的か。pr_review_gate は live 経路を漏れなく強制するか (docs/KB PR との判別が自己申告になっていないか) |
| G2 | main → 本番 (auto-deploy) | デプロイ即実弾のコンポーネント一覧は KB に凍結されているか。新規実弾コンポーネント追加を検知する仕組みはあるか |
| G3 | 実弾コンポーネント台帳 | 実弾を撃てるモジュールの全数列挙 (demo_trader/OandaBridge 経路、status_volume_keeper の直接経路、その他)。各々がどの防御 (emergency_kill / CB / exposure cap / NAV floor) の管轄下か。**管轄マトリクスの空欄 = 本 P10 と同型のギャップ** |
| G4 | 最終防衛の到達性 | emergency_kill は G3 台帳の全コンポーネントを実際に止めるか (名乗りでなく counterfactual テストで)。kill の読み手が全実弾スレッドに存在するか |
| G5 | arm/disarm の権限 | 実弾を新規に arm する変更 (env 有効化、allowed_modes 拡張、lot↑) が user 決裁必須として機械的に守られているか。env 変更の監査ログはあるか |
| G6 | 事後検知 | 意図しない実弾 (タグなし・台帳外の約定) を OANDA transaction 側から検知する読み手はあるか (SVK タグ方式の逆 = タグの無い約定の異常検知) |

## 3. 方法

- 各 G について「名乗る範囲」(ドキュメント/コメント/ガード名) と「実カバー範囲」
  (コード実読 + counterfactual テスト + 本番 API read-only 実測) の差分を取る —
  estimand 監査と同じ規律 (feedback_audit_past_verdicts)
- G3/G4 は**マトリクス形式で全数**: 実弾コンポーネント × 防御層。空欄セルは
  finding として個別に verdict を付ける
- 発見した欠陥は本 P10 と同様 rule:R3 (構造バグ) として個別修理 PR に分割し、
  監査本体 (診断) と執行を混ぜない

## 4. 成功条件 (次回監査の完了定義)

1. G3 の実弾コンポーネント × 防御層マトリクスが KB に凍結され、空欄ゼロ
   (各セル = counterfactual テストへのリンク or 「非管轄と user が明示決裁」)
2. G4: emergency_kill の管轄が「全実弾コンポーネント」であることがテストで pin
   され、新規コンポーネント追加時にマトリクス更新を強制する仕組み (check.py 等) がある
3. G1/G5: live 経路 PR / arm 変更の識別が自己申告でなく機械的
4. G6: 台帳外約定の検知器が読み手付きで存在する (write-only 禁止)

## 5. 明示的な非目標

- 自走マージ原則そのものの見直し (user 決裁事項 — 監査は前提として受け入れ、
  ゲートの実効性のみを問う)
- 戦略のエッジ/統計の監査 (プロセス監査第1波の管轄)
- 本パケットでの修理実施 (起票のみ。keeper × emergency_kill は既に個別修理済み)
