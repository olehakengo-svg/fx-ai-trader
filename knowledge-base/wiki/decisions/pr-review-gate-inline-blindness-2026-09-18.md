# マージゲートの findings 軸は導入以来ずっと恒真だった — 第 3 の空振り形状 (2026-09-18)

**rule**: R3 (構造バグ。365日BT 不要)
**発見経緯**: PR #265 (family A 凍結) で `tools/pr_review_gate.py` が
「P1/P2 指摘なし — マージ可」を返したが、生のレビュー本文を読むと **P2 の inline
finding が 1 件届いていた**。ゲート出力を額面で受け取らなかったので捕捉できた
([[project_review_gate_vacuous_2026_09_11]] の運用が効いた形)。

---

## 1. 欠陥

connector (`chatgpt-codex-connector`) は P1/P2 を **inline review comment
(review thread)** として投げる。旧実装は

```python
payload = _gh_pr_json(pr, "reviews,comments,commits,headRefOid")
findings, arrived = collect_findings(payload)   # reviews + comments のみ
```

しか読まない。`gh pr view --json reviews` が返すのは review の**本文**であって
thread 本文ではないため、**findings は構造的に空**になる。

## 2. 実測 — 空振りは理論ではない

|---|---|---|
| #264 | 6 | 0 |
| #263 | 1 | 0 |
| #261 | 1 | 0 |
| #258 | 1 | 0 |
| #257 | 7 | 0 |
| #256 | 3 | 0 |
| #253 | 6 | 0 |
| #250 | 1 | 0 |
| #249 | 2 | 0 |
| #265 | 1 | 0 |
| **計** | **29** | **0** |

⇒ **ゲート導入 (2026-09-10) 以来、findings 軸は 1 件も観測していない。**
「P1/P2 指摘なし — マージ可」は**恒真命題**だった。

到着判定 (進捗サマリ Completed / 正式 review オブジェクト) は機能していたので、
2026-09-11 の 2 度の修理 ([[project_review_gate_vacuous_2026_09_11]]) は
**到着軸だけを直して findings 軸には触れていなかった**。ゲートの目的は
「消化の強制」なので、実質は空のままだった。

## 3. 差分検証 (修理前 vs 修理後、同一 PR)

```
PR #264  旧: 「P1/P2 指摘なし — マージ可」  → 新: 「P1/P2 指摘 4 件が未消化」
PR #257  旧: 「P1/P2 指摘なし — マージ可」  → 新: 「P1/P2 指摘 7 件が未消化」
PR #253  旧: 「P1/P2 指摘なし — マージ可」  → 新: 「P1/P2 指摘 6 件が未消化」
PR #265  旧: 「P1/P2 指摘なし — マージ可」  → 新: 「1 件は対応 commit で消化済み — マージ可」
```

最後の 1 行が重要 — **消化を検出できている**ので、修理後のゲートは
「何でもブロックする」ようにはなっていない。

## 4. 修理

- `fetch_review_threads(pr)` を新設 (GraphQL `reviewThreads`)。
  `isResolved` / `isOutdated` は消化の positive evidence として除外する
  (解決済みスレッドまでブロックすると実用に耐えない)
- **取得失敗は exit 4 (fail-closed)** — 「取れなかった」を「指摘なし」に折り畳まない
- inline finding の存在自体を**到着の positive evidence** に追加
- 成功メッセージを「**review 本文 + inline thread N 件を検査**」に変更 —
  恒真メッセージは「探した範囲」を名乗らないから恒真だと気付けない

## 4.5 修理版が自分自身の PR で同型の 4 例目を拾った (Codex P2、PR #267)

修理版ゲートを PR #267 自身に通したところ (**MEMORY `project_review_gate_vacuous_2026_09_11`
の「修理 PR 自身をそのゲートに通せ」**を実行)、**exit 3 で 1 件の P2 を返した**:

> `reviewThreads(first:100)` はページングしていないため、thread が 100 を超える PR では
> 先頭ページだけを静かに返す。未解決の P1/P2 が 2 ページ目以降にあり top-level review が
> clean だと、`fetch_review_threads()` は**成功したように見える切り詰めリスト**を返し、
> `evaluate()` が「未解決 finding なし」と誤報する。

**これは本 doc が扱っている欠陥と同じ形状の 4 例目** — 「観測していない対象について
肯定的に断言する」。しかも**修理そのものの中に埋め込まれていた**。

**修理**: `pageInfo{hasNextPage endCursor}` を取り `after` カーソルで全ページ走査。
`hasNextPage` なのに `endCursor` が無い場合と、ページ上限 (100 ページ = 10,000 thread) に
達した場合は **None を返して fail-closed** — 切り詰めたリストを「全部見た」と名乗らせない。

回帰 pin 5 本 (全ページ取得 / **2 ページ目だけに finding がある失敗シナリオ** /
cursor 欠落 fail-closed / ページ上限 fail-closed / repo 解決失敗 fail-closed)。

> ⚠️ #227 版の実装にはページングがあった (既存テスト冒頭の「ページング」記述)。
> §5 のとおり、捨てられた設計に含まれていた性質を 1 つ取りこぼしていた。

## 4.6 5 例目 — ただし「壊れる」という主張は実測で偽だった (Codex P1、PR #267)

ページング追加後の再レビューで **P1**:

> 1 ページ目に空文字を GraphQL cursor として渡している。cursor は opaque token なので
> GitHub が空文字を拒否し、`fetch_review_threads()` が None を返して
> **全 PR で exit 4 になる**。

**実測で反証** (2026-09-18、PR #264 に対し 3 形態を直接実行):

| 呼び方 | rc | nodes |
|---|---|---|
| `-F after=` (空文字) | 0 | 6 |
| `after` 引数なし | 0 | 6 |
| `-F after=null` | 0 | 6 |

⇒ **「GitHub が拒否する / 全 PR で exit 4 になる」は起きていない。**
実際、修理版ゲートはこの指摘が付く前から #264/#257/#253/#265/#267 に対して
正しい差分判定を返していた (§3) — 壊れていたら差分は出ない。

**それでも修正を入れた**理由: 指摘の**推奨自体は正しい**。空文字が通るのは
文書化されていない挙動であり、依存する理由が何もない。1 ページ目は `after` 引数を
**付けない** (`$after` は nullable) のが正しく、コストはゼロ。
回帰 pin 1 本追加 (`test_first_page_omits_the_after_argument`)。

> **記録の要点**: severity の主張 (P1 = 現に壊れている) は偽、推奨 (防御的に直せ) は真。
> レビューは**検証してから採る**のであって、そのまま採るのでも退けるのでもない。
> ここで「P1 と書いてあるから現に壊れている」と記録に残すと、後続が
> 「ゲートは一度全 PR で exit 4 だった」という存在しない履歴を引用することになる。

## 5. 先行実装の存在 (プロセス所見)

**同等の実装は PR #227 に存在し、18 巡のレビューを経て CLOSED (未マージ)** だった
(`fix/review-gate-trigger-watch`、`evaluate(pr: dict)` + `reviewThreads` +
`isResolved/isOutdated` + severity 抽出)。main に着地したのは PR #231 由来の
簡易版で、既存テスト冒頭には「#227 版テスト (GraphQL reviewThreads …) は実装が
異なるため盲目移植していない」と明記されている。

つまり **正しい設計は書かれ、レビューされ、そして捨てられた**。
本修理はその性質を最小差分で main の構造へ移植したもの。

## 6. 教訓

**ゲートの出力は「判定」ではなく「判定の主張」である。**
主張が恒真でないことは、**逆の答えを返すべき既知の入力**で確かめるしかない。
本ゲートは 3 回続けて同じ壊れ方 (到着 2 回・findings 1 回) をしており、
共通形状は「**観測していない対象について肯定的に断言する**」こと。

- 検知器を作ったら、**それが NG を返す実例**を同じコミットで pin する
  (本修理では #264/#257/#253 相当の形状を `test_pr_review_gate_inline.py` に固定)
- 「異常なし」メッセージには**探索範囲を書く**。書けないなら探索していない
- 既存の pin が「空でないこと」を保証していても、**pin が張られている軸**と
  **実際に壊れる軸**が違えば意味がない。#227→#231 の移植判断がまさにそれ
- **修理は同じ欠陥族を持ち込みうる** — 本修理は「観測していない対象を clean と断言する」
  欠陥を直しながら、ページング欠落という形で**同じことをやっていた** (§4.5)。
  だから「修理 PR 自身をそのゲートに通す」が効いた。**検知器の修理は必ず自分自身に適用する**
